# Party Night Engineering Gates

These gates exist so predictable repository, Unity, platform, and multiplayer failures are caught at the cheapest stage possible.

They apply to every Party Night task. A later gate never substitutes for an earlier one.

## 1. Source gate — GitHub before Unity minutes

Every pull request must pass repository checks before Unity Build Automation is run.

Required:
- exact Unity editor pin in `ProjectSettings/ProjectVersion.txt`;
- exact top-level package pins in `Packages/manifest.json`;
- source-controlled `Packages/packages-lock.json` once captured from the pinned editor, because Unity uses it to preserve deterministic dependency resolution;
- valid JSON for package manifests and assembly definitions;
- unique Unity `.meta` GUIDs;
- every tracked asset/folder under `Assets/` has matching metadata;
- no Unity-generated `Library/`, `Temp/`, `Obj/`, `Logs/`, `UserSettings/`, `Build/`, or `Builds/`;
- no conflict markers;
- no backup/obsolete/temp copies;
- no known-dangerous namespace-import patterns;
- build-scene path/GUID consistency when scenes are in scope.

A static pass is repository evidence only. It is never described as a Unity compile.

## 2. Unity compile gate

Unity Build Automation is the authoritative editor environment because the project owner works phone-only.

Every implementation that changes C#, packages, assembly definitions, serialized assets, or project settings must compile in the exact pinned editor before merge.

Current editor:
`6000.3.24f1 (4e7b9b5b6244)`

Rules:
- UBA must checkout the exact PR head being validated;
- auto-detected Unity version must match `ProjectVersion.txt`;
- zero C# compiler errors;
- zero missing project assembly references;
- package resolution must complete;
- do not interpret an UBA "unit test failure" label as an actual assertion failure until the log proves tests executed. Compilation failure during UBA's test phase is a compile failure.

## 3. Test gate

UBA Edit Mode tests run on foundation/editor/configuration changes.

Play Mode tests are now mandatory because Party Night has runtime GameObjects, a local player controller, CharacterController movement, camera behavior, and scene composition.

The target remains configured to fail when required tests fail.

Current UBA test requirement:
- Run project unit tests: ON;
- Edit Mode: ON;
- Play Mode: ON;
- fail the build when any required suite fails: ON.

Tests must cover regressions that already occurred. Examples:
- required build scene exists and is enabled;
- package/editor pins are exact;
- no duplicate authoritative scene ownership.

## 4. Editor/pre-export gate

`PartyNight.Foundation.Editor.ProjectFoundationValidator.PreExport` runs after script compilation and before Player export.

Use it for facts Unity itself must prove:
- exact editor version;
- resolved package versions;
- asset import success;
- build scene presence;
- build settings consistency.

Do not rely on this hook to catch C# compile errors because Unity must compile it before it can run.

## 5. Player-build gate

A change that affects buildability is not complete until the affected Player target exports successfully.

Foundation target:
- Linux desktop 64-bit.

Future platform gates are independent:
- Windows;
- macOS;
- Linux;
- Android;
- Web;
- iOS project generation;
- Linux dedicated server.

Passing Linux never means Web, Android, or iOS is "validated."

## 6. Clean-build policy

Normal script iterations may use UBA Library caching.

Require a clean/non-stale validation run when:
- Unity editor version changes;
- package versions or dependency graph changes;
- core `ProjectSettings` change;
- render pipeline changes;
- input backend changes;
- platform/toolchain configuration changes;
- a build behaves inconsistently with the source;
- preparing a release candidate.

Unity documents incremental builds as the normal path but recommends clean builds when cache state may be stale or corrupted.

## 7. Serialized-asset policy

Do not invent opaque Unity serialized assets just to satisfy CI.

Preferred order:
1. create/save the asset through the pinned Unity Editor;
2. source-control the resulting asset and `.meta`;
3. validate it in a fresh/cloud editor;
4. only hand-author text serialization when the format is understood, minimal, reviewed, and then accepted by the exact Unity editor before merge.

Never keep a temporary generator after its generated asset becomes authoritative.

## 8. Project-settings completeness gate

Before gameplay implementation expands, source control must own the authoritative settings that affect reproducibility.

Known foundation gaps to close deliberately:
- `Packages/packages-lock.json` generated by the pinned editor;
- `ProjectSettings/EditorSettings.asset` with version-control-safe serialization settings;
- `ProjectSettings/ProjectSettings.asset`;
- `ProjectSettings/GraphicsSettings.asset`;
- `ProjectSettings/QualitySettings.asset`;
- platform/build-profile settings as they become active.

Do not copy settings from another game. Generate them with Party Night's pinned editor, review them, then commit them.

## 9. URP gate

Installing the URP package does not activate URP.

Before Party Night art/rendering work begins:
1. create a Party Night URP Asset with a Universal Renderer through Unity;
2. assign it as the default active render pipeline in Graphics settings;
3. review Quality-level overrides;
4. commit the URP asset, renderer asset, settings, and metadata;
5. validate the target platforms affected.

Performance-oriented quality tiers must be intentional for desktop, mobile, and Web.

## 10. Input gate

Gameplay code consumes logical actions, never device keys directly.

Required action vocabulary:
- Move
- Look
- Jump
- Interact
- Grab
- Dash
- UseItem
- Emote

The Input System asset owns bindings/control schemes. Desktop keyboard/mouse, controller, and mobile on-screen controls feed the same logical actions.

Touch UI is not a shrunken desktop layout; safe areas, aspect ratios, interruption, and device variability are separate mobile validation requirements.

## 11. Multiplayer gate

Party Night uses client-server topology with a dedicated authoritative game server.

Server owns important state:
- round lifecycle/timers;
- spawning/elimination;
- scoring/win state;
- pickups/item effects;
- important movement validation;
- durable match result authority.

Clients send intent. Clients do not decide wins, scores, eliminations, inventory, or privileged actions.

Party Night uses dedicated-server authority. Runtime code must not introduce an NGO
`StartHost()` path that makes a player's client the authoritative match server.

Every multiplayer milestone eventually requires tests for:
- multiple clients;
- join/leave;
- reconnect;
- late/duplicate/out-of-order requests;
- latency/loss;
- timeout;
- server restart behavior;
- malformed/unauthorized requests.

## 12. Web networking gate

Browser clients are clients only.

Unity Transport supports WebSocket transport and WebGL clients are constrained to WebSocket-style connectivity rather than ordinary UDP sockets.

Therefore:
- the dedicated server must expose a browser-compatible WebSocket/WSS path;
- browser clients never become authoritative hosts;
- native and browser transports must be validated together before cross-platform multiplayer is claimed.

## 13. Performance gate

Performance is a feature, not post-launch cleanup.

Track by platform:
- CPU frame time;
- GPU frame time;
- allocations/GC;
- draw calls;
- transparency/particles;
- physics;
- animation;
- texture/audio memory;
- network bandwidth;
- scene load memory;
- browser memory;
- mobile thermal/battery behavior.

Hotbox Havoc smoke/fog must scale by quality tier and remain readable.

## 14. Exact-head and merge gate

Before merge:
1. inspect full diff;
2. confirm no unrelated files;
3. confirm no stale/duplicate implementation;
4. confirm exact PR head;
5. pass all applicable static/Unity/test/build gates on that exact head;
6. mark PR ready only afterward;
7. merge with expected-head protection;
8. verify merged result on `main`;
9. close `ACTIVE_TASK.md` with post-merge evidence.

A successful old commit does not validate a newer bookkeeping or fix commit.

## 15. Phone-only rule

No required development gate may depend on the project owner owning a desktop computer.

The required workflow must remain operable from:
- GitHub;
- Unity Build Automation;
- downloadable/uploadable build artifacts and logs;
- the owner's Android test device when Android runtime testing begins.

## 16. Visual progress evidence gate

Once a milestone has visible runtime content, logs alone are insufficient evidence.

Required for visual gameplay milestones:
- render the real Unity runtime scene, not generated concept art;
- capture a deterministic PNG during Play Mode validation;
- keep generated captures outside tracked source;
- include the validated PNG with the Unity Cloud build artifact;
- fail the Unity Cloud build if visual evidence expected by the task is missing;
- inspect the visual artifact before merge for obvious rendering, framing, missing-material, and presentation regressions.

The capture is a development-validation artifact. It is not final marketing art and must not force prototype visuals to become permanent production art.
